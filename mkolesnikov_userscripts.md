# Пользовательские сценарии

### [ Сценарий 1 — Пользователь входит в систему ]

1. Пользователь открывает страницу входа и нажимает кнопку «Continue».
2. Система перенаправляет пользователя в единый сервис аутентификации Keycloak.
3. Пользователь вводит данные учётной записи в форме Keycloak.
4. Пользователь подтверждает вход в систему.
5. Система проверяет учётные данные и возвращает пользователя в веб-приложение.
6. Если данные неверны или сессия не создана, система оставляет пользователя на странице входа и показывает сообщение об ошибке.
7. Если вход выполнен успешно, система показывает в меню разделы Projects, Storage, API keys и Docs.
8. Пользователь открывает раздел Projects и начинает работу со своими академическими целями.

### [ Сценарий 2 — Пользователь создаёт и изменяет проект ]

1. Пользователь открывает раздел Projects и нажимает кнопку создания проекта.
2. Система открывает форму с полями названия, описания, дедлайна, приоритета и направления подготовки.
3. Пользователь вводит название и описание академической цели.
4. Пользователь указывает дедлайн, выбирает приоритет и при необходимости вводит направление в поле Metadata track.
5. Пользователь нажимает кнопку «Create project».
6. Система проверяет обязательное название и корректность даты.
7. Если данные некорректны или сервер отклоняет запрос, система показывает причину ошибки и оставляет форму открытой.
8. Если данные корректны, система создаёт проект и показывает его в списке проектов.
9. Пользователь открывает карточку проекта и переходит в Project settings, чтобы изменить сохранённые параметры или удалить проект с подтверждением.

### [ Сценарий 3 — Пользователь создаёт этап проекта ]

1. Пользователь открывает нужный проект и переходит к списку его этапов.
2. Пользователь нажимает кнопку «Create stage».
3. Система открывает форму с названием этапа, целью, дедлайном и порядковым номером.
4. Пользователь вводит название и кратко описывает результат, которого должен достичь на этапе.
5. Пользователь указывает дедлайн и порядок этапа либо оставляет необязательный дедлайн пустым.
6. Пользователь нажимает кнопку «Create stage».
7. Система проверяет название, дату и целое положительное значение порядка.
8. Если проверка не пройдена или сервер отклоняет запрос, система показывает ошибку и не закрывает форму.
9. Если этап создан, система обновляет список, а пользователь открывает его карточку для работы с задачами.

### [ Сценарий 4 — Пользователь создаёт и редактирует задачу ]

1. Пользователь открывает этап проекта и переходит на его доску задач.
2. Пользователь нажимает кнопку «Create task».
3. Система открывает форму с результатом задачи, сложностью, дедлайном, приоритетом и количеством частей по трём блокам.
4. Пользователь формулирует ожидаемый результат и указывает сложность от 1 до 10.
5. Пользователь задаёт приоритет, при необходимости указывает дедлайн и распределяет части между пониманием, запоминанием и практикой.
6. Пользователь нажимает кнопку «Create task».
7. Система проверяет результат, числовые поля и наличие хотя бы одной части задачи.
8. Если проверка или сохранение завершились ошибкой, система показывает сообщение и сохраняет введённые данные формы.
9. Если задача создана, система пересчитывает её начальные веса и показывает задачу на доске, где пользователь может открыть редактирование.

### [ Сценарий 5 — Пользователь настраивает параметры расчёта ]

1. Пользователь открывает настройки проекта и переходит к разделу политик.
2. Система загружает текущие политики агрегации, калибровки, рекомендаций и риска.
3. Пользователь изменяет веса приоритета и срочности для агрегации показателей.
4. Пользователь задаёт порог разрыва и множитель штрафа для калибровки.
5. Пользователь задаёт пороги приемлемого, низкого и критического уровня, а также максимальное количество рекомендаций.
6. Пользователь настраивает пороги риска для этапов и задач и задаёт порог ложной уверенности.
7. Пользователь нажимает кнопку сохранения изменённого раздела политики.
8. Система проверяет диапазоны значений и показывает сообщение об ошибке, если число выходит за допустимые пределы.
9. Если данные корректны, система сохраняет политику и обновляет её значения при следующем открытии настроек.

### [ Сценарий 6 — Пользователь оценивает состояние задачи ]

1. Пользователь открывает задачу на странице этапа.
2. Система показывает текущий статус задачи, оценки блоков, готовность, прогноз снижения и рекомендации.
3. Пользователь нажимает кнопку «Record assessment».
4. Система открывает форму выбора блока: comprehension, memorization или practice.
5. Пользователь выбирает блок и вводит самооценку от 0 до 100.
6. Пользователь нажимает кнопку «Save assessment».
7. Система проверяет диапазон оценки и сохраняет снимок с текущим временем и источником ручного подтверждения.
8. Если значение не является числом от 0 до 100 или запрос не выполнен, система показывает ошибку и не закрывает форму.
9. Если оценка сохранена, система обновляет оценки задачи и связанные показатели готовности.

### [ Сценарий 7 — Пользователь изменяет веса задачи и её статус ]

1. Пользователь открывает задачу и нажимает кнопку настройки весов.
2. Система показывает текущие доли понимания, запоминания и практики.
3. Пользователь изменяет количество частей для каждого блока.
4. Система пересчитывает процентные веса блоков и показывает результат до сохранения.
5. Пользователь нажимает кнопку сохранения весов.
6. Если сумма частей равна нулю или введено отрицательное либо нечисловое значение, система показывает ошибку и не отправляет запрос.
7. Если веса корректны, система сохраняет их и обновляет экран готовности задачи.
8. Пользователь выбирает новый допустимый статус задачи, например learning, at_risk или stable.
9. Система обновляет статус, а при ошибке сервера показывает сообщение и сохраняет прежний статус.

### [ Сценарий 8 — Пользователь анализирует прогресс подготовки ]

1. Пользователь открывает дашборд проекта.
2. Система получает актуальные данные проекта и связанных этапов и задач.
3. Система показывает метрики coverage и readiness now в виде значений и прогресс-баров.
4. Система показывает дедлайн проекта, приоритет, текущий статус и уровень риска.
5. Пользователь просматривает список этапов и агрегированные показатели по ним.
6. Пользователь открывает блок Critical to deadline и изучает задачи, которые могут помешать достижению цели.
7. Система показывает ошибку загрузки, если дашборд или его read-модель недоступны.
8. Пользователь открывает задачу из этапа, чтобы изучить её оценки и получить рекомендацию по следующему действию.
9. После новой оценки система обновляет дашборд и отображает изменившиеся readiness, coverage и риск.

### [ Сценарий 9 — Пользователь создаёт библиотеку учебных материалов ]

1. Пользователь открывает раздел Storage и нажимает кнопку «Create library».
2. Система открывает форму названия, описания, публичности и первоначального доступа.
3. Пользователь вводит название и описание библиотеки.
4. Пользователь выбирает публичную библиотеку либо оставляет библиотеку приватной.
5. Для приватной библиотеки пользователь добавляет идентификаторы пользователей и назначает им роли reader или writer.
6. Пользователь нажимает кнопку создания библиотеки.
7. Система проверяет название и требует хотя бы одного пользователя для приватной библиотеки.
8. Если проверка или запрос завершились ошибкой, система показывает причину и оставляет форму открытой.
9. Если библиотека создана, система добавляет её в список и позволяет открыть дерево файлов.

### [ Сценарий 10 — Пользователь размещает учебные файлы в библиотеке ]

1. Пользователь открывает дерево нужной библиотеки и выбирает текущую папку.
2. Пользователь нажимает кнопку «Create folder» и вводит название новой папки.
3. Система проверяет название папки и создаёт её в выбранном расположении.
4. Пользователь открывает папку и нажимает кнопку загрузки файла.
5. Пользователь выбирает файл поддерживаемого типа и запускает загрузку.
6. Система проверяет расширение, MIME-тип и размер файла, который не должен превышать 500 МБ.
7. Система показывает ход загрузки и позволяет отменить операцию до её завершения.
8. Если файл не поддерживается, размер превышен или у пользователя нет права записи, система показывает причину и предлагает повторить загрузку.
9. Если загрузка завершена, система подтверждает файл и обновляет содержимое текущей папки.

### [ Сценарий 11 — Пользователь удаляет материалы из библиотеки ]

1. Пользователь открывает дерево библиотеки и переходит к нужной папке.
2. Пользователь выбирает один файл или папку в таблице содержимого.
3. Пользователь выбирает дополнительные элементы с помощью множественного выделения.
4. Система активирует действие удаления для выбранных элементов.
5. Пользователь нажимает кнопку удаления и подтверждает операцию.
6. Система отправляет запрос на удаление выбранных файлов или папок.
7. Если выбранный объект уже отсутствует или у пользователя нет права удаления, система показывает ошибку и не скрывает его из списка.
8. Если удаление выполнено, система обновляет дерево и содержимое текущей папки.
9. Пользователь проверяет, что удалённые элементы больше не отображаются в библиотеке.

### [ Сценарий 12 — Пользователь создаёт ключ для внешнего API ]

1. Пользователь открывает раздел API keys.
2. Система показывает существующие ключи и их состояния active, expired или revoked.
3. Пользователь вводит название нового ключа.
4. Пользователь при необходимости указывает дату истечения срока действия.
5. Пользователь выбирает области доступа к projects и storage с правами чтения или записи либо применяет готовый набор разрешений.
6. Пользователь нажимает кнопку создания API-ключа.
7. Система проверяет название, дату и наличие хотя бы одной допустимой области доступа.
8. Если данные некорректны или сервер отклоняет запрос, система показывает ошибку и не создаёт ключ.
9. Если ключ создан, система показывает секрет один раз, предлагает скопировать его и добавляет ключ со статусом active в список.

### [ Сценарий 13 — Пользователь отзывает или обновляет ключ API ]

1. Пользователь открывает список API-ключей и выбирает активный ключ.
2. Пользователь запускает операцию отзыва ключа.
3. Система запрашивает подтверждение операции, которая прекращает действие секрета.
4. Пользователь подтверждает отзыв.
5. Система отправляет запрос и помечает ключ как revoked либо показывает ошибку сохранения.
6. Для действующего ключа пользователь запускает операцию ротации.
7. Система создаёт новый секрет для того же ключа и показывает его пользователю для копирования.
8. Пользователь заменяет старый секрет во внешнем клиенте и проверяет доступ с выбранными областями.
9. Если ключ истёк или отозван, система отображает соответствующее состояние и не использует его для новых запросов.
